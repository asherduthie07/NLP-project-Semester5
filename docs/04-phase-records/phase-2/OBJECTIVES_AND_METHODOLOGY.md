# Phase II objectives and methodology

Phase I acceptance was PASS in `../phase-1/FINAL_VERIFICATION_AUDIT.md`. This phase extends the existing immutable snapshot and preprocessing jobs with static structure extraction and measured exploratory analysis. It does not execute imported code or generate AI descriptions. The original UI specification remains unchanged; frontend M1 remains the only authorized milestone.

Flow: import snapshot → default versioned Phase I preprocessing job → independent Phase II analysis job → deterministic CAIR symbols/edges/endpoints → repository resolution and statistics → PostgreSQL result and relational symbol/edge rows → typed API. The analysis endpoint returns 409 `preprocessing_pending` while an asynchronously dispatched preprocessing job is in progress; repeat the request once it completes. Repeated analysis of the same snapshot and preprocessing job returns the same stable job ID and result.

Python extraction uses `ast.parse`, never import/eval. Syntax failure retains the module record and a source-linked warning; Phase I lexical results remain intact. It records classes, nested functions, async/static/class methods, constructors, assignments, imports with aliases, decorators, bases and conservative calls. Java uses the pinned Tree-sitter grammar and traverses declaration nodes, preserving partial findings and a warning on malformed syntax. Java overload identity includes the full textual parameter signature. Java type resolution is not claimed.

Resolution is intentionally conservative: exact imported module names resolve within the snapshot; missing absolute imports are classified external and missing relative imports unresolved. Unique class names can resolve inheritance; multiple candidates are ambiguous. Bare local calls resolve only with one local candidate. Attribute calls stay unresolved unless proven. Containment is always confirmed. Module import cycles use Tarjan strongly connected components.

Statistics are computed from the immutable Phase I result, not guessed. Source code tokens exclude comment tokens for vocabulary/diversity. Documentation terms come only from extracted comments/docstrings/JavaDoc. Duplicates remain in corpus totals. The exact measured report is `../../07-findings/phase-2/analysis.json`.

Metric definitions: `tokens` includes all lexical records; `vocabulary_size` counts distinct non-comment token spellings; `lexical_diversity` divides vocabulary by non-comment token count (zero for empty); `comment_lines` sums inclusive line spans of non-Python-docstring comments, so overlapping lines may count twice; `documentation_coverage` divides documented class/function/method/constructor/interface/enum/record symbols by all such symbols (zero for empty); `function_lengths` and `class_sizes` use inclusive declaration spans; `module_fan_in/out` count confirmed import edges, not unique neighbors. Naming patterns count identifier occurrences by spelling shape. No natural-language interpretation is assigned to punctuation/operator frequencies.

Phase II quality gate requires Python/Java extraction and source references, stable persisted CAIR, conservative dependencies, measured EDA, typed graph/overview API, integration/regression tests and honest limitations. An independently reviewed annotation set is still needed for precision/recall/F1; the current assertion fixtures are implementation tests and are not represented as a benchmark.
